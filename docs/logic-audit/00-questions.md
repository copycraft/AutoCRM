# Logic audit: open questions

Where intent is ambiguous or two sources disagree. Nothing listed here was "fixed" on the strength of a guess; each needs an answer from the product owner.


## Auth & access

1. **Q-AUTH-1 — Web wrong-password message.** The login page passes `t('invalidCredentials')` ("Hibás e-mail vagy jelszó") only as the *fallback* (`frontend/src/app/[locale]/login/page.tsx:55`), but `errorMessage` resolves the 401 code `unauthenticated` through the catalogue first (`frontend/src/lib/api/errors.ts:86-89`), which gives "Nincs bejelentkezve. Kérjük, jelentkezzen be újra." (`frontend/src/messages/hu.json:673`). Which text is intended on a failed login? Android shows "Hibás e-mail vagy jelszó." (`android/.../ui/login/LoginScreen.kt:100`).
2. **Q-AUTH-2 — Lockout on Android.** The backend signals lockout as HTTP 429 `too_many_requests` (`backend/src/error.rs:104-108`), but Android maps 429 to `Server` (retryable, `android/.../data/api/AutoCrmApi.kt:145`) and looks for a code `account_locked` that the backend never emits (`android/.../ui/login/LoginScreen.kt:102`, `ChangePasswordScreen.kt:108`). What should the phone show when the account is locked, and should it say "Szólj az irodának" (admin reset unlocks it, AUTH-56) or "wait 15 minutes" (web `hu.json:695`)?
3. **Q-AUTH-3 — Lockout counts only wrong passwords of existing accounts; is the lock enforced when the lock expires mid-count?** `record_failed_login` keeps incrementing `failed_logins` after the lock expires, so after the lock the 11th wrong attempt immediately re-locks (`backend/src/repo/users.rs:141-154`). DECISIONS says "10 failed logins lock the account for 15 minutes" (`docs/DECISIONS.md:138`). Should the counter restart after a lock expires (10 more tries), or should every further failure re-lock?
4. **Q-AUTH-4 — Can viewers write tasks?** `role.rs:18-19` and `docs/API.md:28` ("Everyone signed in can read. Writes need a capability") and the test `viewer_cannot_write_anything` (`backend/src/domain/role.rs:69-92`) say viewers write nothing, but `backend/src/api/tasks.rs:3-4` deliberately lets any authenticated user create/toggle/delete tasks. Also: may any user delete anyone's task? Need a product decision.
5. **Q-AUTH-5 — "New password must differ from current."** Android enforces it (`android/.../ui/login/ChangePasswordScreen.kt:67-70`); the backend (`backend/src/service/auth.rs:219-241`) and web (`frontend/src/app/[locale]/password/page.tsx:27-31`) do not. Is this a real rule (then backend must enforce it) or an Android-only nicety?
6. **Q-AUTH-6 — Voluntary password change and its entry point on web.** `/password` is a standalone page whose copy says the change is required at first login (`frontend/src/app/[locale]/password/page.tsx:50`, `hu.json:110`), and nothing links to it except the forced redirect; it is not wrapped in `AppShell`, so it has no auth gate. Should signed-in users be able to change their password voluntarily (from Preferences), and what should an unauthenticated visitor to `/password` see?
7. **Q-AUTH-7 — Web message for `wrong_password`.** The backend returns 422 `wrong_password` with English "current password is incorrect" (`backend/src/service/auth.rs:230-233`); the web catalogue has no `wrongPassword` key (`frontend/src/messages/hu.json:666-700`), so the English backend text is shown. Is a Hungarian message expected (Android: "Hibás a jelenlegi jelszó.")? Same for `too long` validation text.
8. **Q-AUTH-8 — Expired/revoked session on Android mid-use.** Android shows "A munkamenet lejárt. Jelentkezz be újra." on 401 (`android/.../ui/common/Errors.kt:27`) but nothing clears the stored token or returns to the login screen (only explicit logout/server change clear it: `MainActivity.kt:266-267`, `ServerSetupScreen.kt:125`). Web returns to login on 401 only via the `/auth/me` query (`AppShell.tsx:56-58`); a 401 on another query leaves the user on the page. Is automatic sign-out on any 401 expected on both clients (docs/history/FRONTEND_PLAN.md:193 says "401 returns to login")?
9. **Q-AUTH-9 — Role change while a session is open vs. cached role on clients.** The backend revokes sessions on role change (AUTH-55) and reads the role live (AUTH-21), but Android caches `role` in DataStore at login (`SessionStore.kt:77-87`) and only refreshes it after a password change. After re-login the value is fresh; is any refresh of cached role/`must_change_password` expected at app start (e.g. calling `/auth/me`)? E.g. an admin reset (AUTH-56) sets `must_change_password=true` but revokes the phone's session, so the phone will just 401 (Q-AUTH-8) rather than route to the change screen.
10. **Q-AUTH-10 — Web login without `Origin`.** Login-CSRF is only checked when an `Origin` header is present (`backend/src/api/auth.rs:114`), while `check_origin` treats a missing Origin as failure for other cookie writes (`backend/src/api/extract.rs:77-79`). Is skipping the check on Origin-less web logins intended (for non-browser/tools), given browsers always send Origin on POST?
11. **Q-AUTH-11 — Last-admin guard race.** The count check (`backend/src/api/users.rs:115`) runs inside a transaction without a lock, so two concurrent demotions of the last two admins could both pass. DECISIONS says the last admin "can't be demoted or deactivated" (`docs/DECISIONS.md:140`). Is a strict guarantee required (serialisable/locked), or is best-effort acceptable for <20 users?
12. **Q-AUTH-12 — Web message for `last_admin`.** Catalogue text says only "cannot be disabled" ("nem tiltható le", `frontend/src/messages/hu.json:692`), backend covers demote *or* deactivate (`backend/src/api/users.rs:117-118`). Should the text also cover demotion?
13. **Q-AUTH-13 — Session management UI.** `GET /auth/sessions` / `DELETE /auth/sessions/{id}` and admin revoke exist, and `SessionStore.kt:22` claims "an admin can revoke from `/auth/sessions`" — but that endpoint only lists/revokes the caller's *own* sessions (`backend/src/api/auth.rs:221-252`); an admin can only revoke *all* sessions of another user (`backend/src/api/users.rs:206-213`). Is per-device revocation by an admin intended? (UI absence is already C12.)
14. **Q-AUTH-14 — Admin UI for users.** `hu.json:652-666` has a full `users` namespace (new/edit user, temporary password, revoke sessions, role labels) and docs/history/FRONTEND_PLAN.md:102 lists "Settings — users/roles", but `/admin` is `UnavailableState` (`frontend/src/app/[locale]/admin/page.tsx:12`) and nothing calls `usersApi`. Confirm the intended location and scope of the user admin screen (overlaps C8).
15. **Q-AUTH-15 — Deactivated user with correct password.** Login returns the generic 401 for an inactive account (`backend/src/service/auth.rs:155-157`), but only *after* verifying the password, and a correct password on an inactive account does not reset or increment `failed_logins`. Should a disabled user get a distinct message ("account disabled") or stay indistinguishable (AUTH-06)?

## Sales pipeline

1. **Q-SALES-1 Repeat conversion vs. UI and docs.** Backend and migration say a lead may be converted repeatedly (backend/src/service/leads.rs:69-71; 0011_relations_quotes_suppliers.sql:35-39), and the web page comment agrees (frontend/src/app/[locale]/leads/[id]/page.tsx:110-111). But the same page hides the Convert button once `orders.length > 0` (:147-156). docs/API.md:20 still lists 409 `already_converted`, and hu.json:678 keeps "alreadyConverted". Android shows "Megrendeléssé" regardless (android/.../ui/leads/LeadScreens.kt:385-397). Need: should a second conversion be reachable from the web UI, and should `already_converted` be removed from the docs?
2. **Q-SALES-2 Which lead stages allow conversion?** `convert` does not check the current stage (backend/src/service/leads.rs:58-111), so a `lost` lead converts straight to `won`. A manual move out of a terminal stage requires a note (backend/src/domain/stage.rs:122-128). Need: may a `lost` lead be converted without a reopen note, and may a lead already in `won` convert again (it would insert `won`→`won`)?
3. **Q-SALES-3 What should conversion copy from the quote?** The quoted value, currency and validity are not carried over. The web pre-fills currency from the partner, not from `lead.currency` (frontend/src/components/forms/LeadConvertDialog.tsx:52-55), and sends `items: []` (:65). Android always sends `currency = "HUF"` (android/.../ui/leads/LeadScreens.kt:307,506), which conflicts with the docs/history/REMEDIATION.md:13 / docs/history/AUDIT.md MAJOR-03 fix. Need: the intended prefill source (lead quote currency, then partner default?) and whether a quoted value should become a line item.
4. **Q-SALES-4 Do lead documents move to the order on conversion?** `Owner::from_about` says "an order wins when both are present: the document belongs to the job by then" (backend/src/repo/documents.rs:50-56). But `documents_one_owner` allows only one owner (0012_documents_on_leads.sql:14-15), and conversion copies or moves no documents (backend/src/service/leads.rs:58-111). Need: should the quotation PDF stay on the lead, be visible from the order, or be re-owned?
5. **Q-SALES-5 Lead PATCH does not re-check partner/contact consistency.** Create validates that the partner exists and that the contact belongs to it (backend/src/service/leads.rs:17-31). PATCH writes any `partner_id`/`contact_id` (backend/src/api/leads.rs:230-244), and the web form does not reset the contact when the partner changes (frontend/src/components/forms/LeadForm.tsx:157-163,214). Need: confirm the same rule applies on update.
6. **Q-SALES-6 Archived partners on leads.** Archived partners "do not appear in new selections" (frontend/src/messages/hu.json:152), and orders refuse them (backend/src/service/orders.rs:56-58). Lead create/update accepts an archived partner (backend/src/service/leads.rs:17-21). Need: should a lead be refused, or only warned, for an archived partner?
7. **Q-SALES-7 Supplier filter in pickers.** 0011_relations_quotes_suppliers.sql:27-29 says the flag exists because suppliers turn up in the customer picker. The web `PartnerPicker` never sends `role=customer` (frontend/src/components/forms/PartnerPicker.tsx:41-44). Need: should lead/order partner pickers filter `role=customer`?
8. **Q-SALES-8 Role editing and defaulting differ by client.** The web `PartnerForm` has no role field at all (frontend/src/components/forms/PartnerForm.tsx:13-27). Android defaults an unclassified partner to `customer` and sends it on save (android/.../ui/partners/PartnerEditScreen.kt:42,64,97). The column comment says "Set deliberately" (0011:33). The audit diff on partner update omits `role` (backend/src/api/partners.rs:324-358). Need: may Android silently classify on save, and should role changes be audited?
9. **Q-SALES-9 Depth of Hungarian tax-number validation.** The code checks only 11 digits (backend/src/domain/partner.rs:15-31). The statutory format has a VAT-code digit of 1–5 and a check digit (SALES-06). The web catalogue has an unused "Érvénytelen adószám formátum" string (frontend/src/messages/hu.json:816) and the form has no client-side check. Need: is checksum/VAT-code validation wanted, and should `country=HU` require a tax number for `kind=business`?
10. **Q-SALES-10 Deduplication of partners and contacts.** There is no uniqueness on partner name or tax number and no duplicate warning (backend/migrations/0002_partners_leads.sql:5-27; backend/src/api/partners.rs:181-216). Only vehicles dedupe (SALES-27), and `duplicate` 409 exists in docs/API.md:20. Need: should creating a partner with an existing tax number be refused or warned?
11. **Q-SALES-11 Semantics of PATCH /documents/{id}.** docs/API.md:27 says an omitted field keeps its value. `set_validity` overwrites issuer, valid_from, valid_until and vehicle_id with whatever is sent, so an omitted field is cleared (backend/src/api/media.rs:322-360; backend/src/repo/documents.rs:274-282). The validity check also only compares two dates both present in the body, not against stored values. Need: partial or full-replace semantics?
12. **Q-SALES-12 Uploading `invoice`/`proforma` kinds.** `invoice` is "generated, never uploaded" (backend/src/domain/media.rs:51-52), yet `UploadTarget::Document { kind }` accepts any kind, including on a lead (backend/src/media/upload_token.rs:21-24; backend/src/service/media.rs:150-164). Need: which kinds may be uploaded, and to which owner?
13. **Q-SALES-13 Web cannot upload lead documents.** The API exists (backend/src/api/media.rs:63-80), and the lead page lists documents but has no upload control. The frontend endpoints only wrap `/orders/{id}/uploads` (frontend/src/lib/api/endpoints.ts:182). Need: is a lead upload UI expected on web and/or Android? (Related to integration-audit C5/D1.)
14. **Q-SALES-14 Timezone for "quote expired".** The web uses the Europe/Budapest date (frontend/src/app/[locale]/leads/[id]/page.tsx:31-36). Android uses the device `LocalDate.now()` (android/.../ui/leads/LeadScreens.kt:474-475). This is a specific case of integration-audit A5. Need: confirm Budapest business date on all clients.
15. **Q-SALES-15 Does sending a quotation move the lead to `quoted`?** `send_quotation` queues mail only and changes no stage (backend/src/service/email.rs:637-783). docs/history/VIABILITY.md:275 warns that `quoted` "becomes a checkbox somebody ticks late or never". Need: should sending (or setting `quoted_value_minor`) advance the stage automatically?
16. **Q-SALES-16 Stale API docs for sales routes.** docs/API.md:52 omits the `role` filter. :58 says the partner detail is "partner + contacts + orders" (the code also returns `leads`). :69 omits the quote fields. :70 says "converted order ref" (singular). Need: confirm the code is authoritative. Also: the web partner detail page renders no leads section, although `PartnerDetail.leads` exists for exactly that purpose (backend/src/api/partners.rs:223-225). Should it?
17. **Q-SALES-17 The spec body is ignored on conversion.** `POST /orders` writes a build `spec` in the same transaction (backend/src/api/orders.rs:172-175,360-369). `convert` accepts `OrderBody` but never reads `spec`, and it drops the project type's spec requirement (backend/src/api/leads.rs:351-381). Need: must a converted order also accept or require the build spec?

## Order lifecycle

1. **Q-ORD-1: Which client can satisfy the MEO gate?** The MEO gate needs ≥1 `completion` image (backend/migrations/0002_partners_leads.sql:81; docs/history/VIABILITY.md:277 calls it "real leverage"). Android restricts manual attaching to `production` only (android/.../data/prefs/CapturePrefs.kt:90-95; OrderPhotoSection.kt:85-96). The web has no image-upload UI (only the endpoint, frontend/src/lib/api/endpoints.ts:182). Which flow is supposed to produce `completion` photos? Is it the inspection/handover flow, and if so, does that write category `completion` or `inspection`?
2. **Q-ORD-2: Can a designer leave `intake`?** Designers may change stages (backend/src/domain/role.rs:58-60), but leaving `intake` requires `mileage_in` (backend/src/service/stages.rs:131-145), and only `EditOrders` (admin/office) may record it (backend/src/api/orders.rs:584; web editable only for canEdit, page.tsx:481). Is it intended that a designer can never move an order out of `intake` alone?
3. **Q-ORD-3: Should `/transitions` report the intake-slip gate?** The endpoint's `gates_met` reflects only image gates (backend/src/service/stages.rs:26-40,60-62), so every target from `intake` shows as allowed and then fails with 422 `intake_slip_missing` (stages.rs:131-145). Its doc says it lets the UI present targets "without reimplementing the transition rules" (stages.rs:26-29). Should the intake-slip gate be reflected there, for example as `gates_met = false` or a separate flag?
4. **Q-ORD-4: Does cancellation need the intake slip?** The intake-slip gate also blocks `intake` → `cancelled` (backend/src/service/stages.rs:135: any `to != intake`). The docs say exit stages are "reachable from any open stage without gates" (docs/DECISIONS.md:57; backend/src/domain/stage.rs:10). Must an order be cancellable from intake without a mileage reading?
5. **Q-ORD-5: Is `completed` → `cancelled` a reopen that needs a note?** Because the terminal check runs before the exit check (backend/src/domain/stage.rs:122-131), it is classed as a `reopen` requiring a note. Is cancelling a finished order meant to be a reopen that needs a note, or an exit? Is it allowed at all?
6. **Q-ORD-6: Should the web intake slip keep the "not recorded" state?** The web always sends `valuables_declared: hasValuables` (a boolean) when saving the slip (frontend/src/components/orders/IntakeSlipSection.tsx:42,65). That turns "not recorded" (NULL) into "recorded, nothing in the car" (`false`). The migration insists these are different defences (backend/migrations/0019_intake_extras.sql:9-14; backend/src/api/orders.rs:166-168). Should the web offer a third "not asked" state, or send the field only when the user touched it?
7. **Q-ORD-7: Is a tasks feature intended?** backend/migrations/0009_order_notes.sql:5 says "AutoCRM has no to-do feature and is not gaining one". backend/migrations/0017_tasks.sql:1-3 and backend/src/api/tasks.rs add follow-up tasks. Which statement is current? Should 0009's comment be treated as superseded?
8. **Q-ORD-8: Who may delete or toggle a task?** Any user may delete or toggle any task, including other people's (backend/src/api/tasks.rs:1-6,141-167). The web offers delete only on open tasks (frontend/src/components/tasks/TaskList.tsx:188-193). Android offers delete on open and done tasks (android/.../ui/tasks/TasksScreen.kt:168,179). Should deleting someone else's task, or a done task, be allowed?
9. **Q-ORD-9: Capture-first or job-first photos?** Commit 701a0ec's message says photos are added "from inside a job", because "choosing the job afterwards is how photos land on the wrong one". The working tree re-introduces capture-first photography through the picker (android/.../MainActivity.kt:350-364; ui/capture/CaptureScreen.kt:57-60). Which is the intended product rule? Does the answer also retire the sticky current order (E1/E2)?
10. **Q-ORD-10: Should terminal stages lock orders?** No rule locks items, the spec, the intake slip, or blockers once an order is `completed` or `cancelled` (backend/src/api/orders.rs:578-1081 has no stage check). Invoicing may depend on items. Should edits to terminal orders be refused, audited only, or remain free?
11. **Q-ORD-11: Does cancelling resolve blockers?** When an order is cancelled, its open blockers stay open and continue to be nudged (docs/history/VIABILITY.md:39; nudge candidates ignore stage, backend/src/repo/blockers.rs:191-196). Should cancelling (or completing) auto-resolve blockers or at least stop nudges?
12. **Q-ORD-12: Are catalogues missing error codes?** docs/API.md:21 lists the 422 codes but omits `intake_slip_missing`. docs/API.md:20 lists 409 codes but omits `not_resolved`, which also has no web catalogue entry (hu.json:669-716). Should these codes be added to the documented catalogue, or are they meant to fall back to the backend message?
13. **Q-ORD-13: Which note text is right, and does a reopen send the progress mail?** The web's `note_required` message says only "A visszalépéshez indoklás szükséges." (backward), while the same code also covers reopen (backend/src/domain/stage.rs:78; hu.json:682 vs 326 "Hátra- vagy újranyitáskor kötelező."). Is a reopen supposed to trigger the progress mail? Currently only `forward` does (backend/src/service/stages.rs:161).

## Inspection & media

1. Q-INSP-1: In-app camera for inspections. Commit 701a0ec says "CameraX, the CAMERA permission and the capture screen are gone" because CameraX can't match the system camera's quality for evidence (`git show 701a0ec`; A:ui/photos/OrderPhotoSection.kt:48-52). But A:ui/inspection/CameraCapture.kt:56-63, 118-119 is a CameraX live-view camera that every inspection photo must go through. Which is intended for inspections: in-app camera only, or the system camera app?
2. Q-INSP-2: What should happen when the session expires during upload? A:data/upload/UploadWorker.kt:34-36 says rows stay and "signing in enqueues this again". But a 401 mid-upload marks the row `blocked` (A:data/upload/Uploader.kt:96-98, 137), and nothing in the login flow re-enqueues the worker (only A:AutoCrmApp.kt:58 and capture). Should an expired session pause the queue and resume after login, or block the rows until the user taps "Újra"?
3. Q-INSP-3: Do unsigned drafts sync? `pendingSync()` returns every `draft`/`syncing` row (A:data/db/InspectionDraft.kt:60-61), the worker runs at app start (A:AutoCrmApp.kt:60), and `syncDraft` never checks `payload.signed` before it calls `signInspection` (A:data/inspection/InspectionSync.kt:225). But the ViewModel says the worker "performs the server sign" after local sign-off (A:ui/inspection/WalkaroundViewModel.kt:502, 540-545), and the home screen treats `signed` as the "waiting for upload" state (A:ui/inspection/InspectionHomeScreen.kt:112). Should an unsigned draft sync partially (create a server draft), not sync at all, or be signed?
4. Q-INSP-4: Can media referenced by a signed inspection be deleted? The inspection is "immutable once signed" (backend/migrations/0026_inspections.sql:8-9, 99-100), but inspection images are mutable rows that `DeleteMedia` can soft-delete (backend/src/domain/media.rs:15-18; backend/src/api/media.rs:217-233). The detail then silently shows null URLs (backend/src/api/inspections.rs:261-274). Signature documents are only protected against hard delete (`ON DELETE RESTRICT`, 0026_inspections.sql:93). Should delete be refused for images or documents attached to a signed inspection?
5. Q-INSP-5: Cross-category dedupe. Server dedupe is per `(order_id, sha256)` and ignores category (backend/src/service/media.rs:137-142; 0004_media.sql:30-32). So bytes already on the order as `production` return `already_uploaded` with a production image, and the inspection attach then fails with "image is not an inspection photo" (backend/src/api/inspections.rs:455-457). Is that acceptable, given that inspection photos should be fresh captures, or should the category be part of the identity?
6. Q-INSP-6: What do the template flags `optional` and `required` mean? Both are stored (0026_inspections.sql:120-121; backend/src/api/inspections.rs:833-834). The seed only sets `optional` (roof), and the phone checks only `optional` when it enforces overview photos (A:ui/inspection/WalkaroundViewModel.kt:506-510). What is `required` for, and what does `optional=true, required=true` mean?
7. Q-INSP-7: Is the web meant to write verdicts? The API header says "the web reads history, comparisons and zone templates" (backend/src/api/inspections.rs:5-6). The web component says it "reviews check-in verdicts" and has verdict buttons (frontend/src/components/inspections/InspectionSection.tsx:4-5, 249, 305-331). Those buttons also show on signed check-ins, where the server answers 422 `locked`. Also, a later phone sync upserts its own verdicts over any web verdict (A:data/inspection/InspectionSync.kt:209-223; backend/src/repo/inspections.rs:380-386). Who owns verdicts, and should the web hide the buttons once signed?
8. Q-INSP-8: Notes on drafts. The migration calls notes "follow-up annotations on a locked inspection" (0026_inspections.sql:99-100), but `add_note` accepts any status (backend/src/api/inspections.rs:663-665), and the web composer shows for drafts too (InspectionSection.tsx:218-219). Should notes be allowed on drafts?
9. Q-INSP-9: Several check-in drafts per order. There is a unique index for draft check-outs only (0026_inspections.sql:38-41), so nothing prevents several draft check-ins per order, or a check-in while a newer draft check-out exists. Is that intended?
10. Q-INSP-10: Which check-out does an offline check-in compare against? The phone links `checkoutServerId` by max `signedAt` string when online (A:ui/inspection/WalkaroundViewModel.kt:178-186) and uses it for the on-device comparison. The server always re-links to its latest signed check-out at create time (backend/src/api/inspections.rs:172-186), and the phone's `checkoutDamageId` values may belong to a different check-out, which gives a 400 at verdict sync (api/inspections.rs:770-779). Which check-out is authoritative when a newer one is signed between walkaround and sync?
11. Q-INSP-11: How should suggestions and links work? The suggestion takes the *first* same-zone, same-type check-out damage (backend/src/api/inspections.rs:716-719), so several check-in damages can match the same check-out damage. A `preexisting` verdict is accepted with `checkout_damage_id = null` (api/inspections.rs:770), and the Android "Megvolt" chip sends `match?.id`, which may be null (A:ui/inspection/InspectionFinishScreens.kt:165-167). Must a `preexisting` verdict name a check-out damage, and may one check-out damage explain several check-in damages?
12. Q-INSP-12: Does "Újra" replace one shot or all of them? Retake removes *all* unattached photos with the same zone, purpose and damage from the draft (A:ui/inspection/WalkaroundViewModel.kt:332-338), but deletes only the reviewed file and queue row (:319-327). Earlier kept shots of that zone (e.g. several overviews, "Még egy közeli") disappear from the payload while their queue rows remain. Should retake replace only the last shot?
13. Q-INSP-13: Comparison before signing. `signNow` requires `s.comparison != null` when verdicts are pending (A:ui/inspection/WalkaroundViewModel.kt:531), and the Comparison screen says skipping is fine because "aláíráskor úgyis kell" (InspectionFinishScreens.kt:78). E3 already reports that `comparison` is never set. Separately: must a check-in with zero damages still load the comparison before it can be signed, or only when there are damages to review?
14. Q-INSP-14: Doc drift on categories and file types. docs/API.md:107 lists image categories as intake|production|completion|marketing, without `inspection` (added by 0025). Android names every queued file and filename `.jpg` and defaults the content type to `image/jpeg` (A:data/upload/UploadQueue.kt:70, 85, 125). Gallery picks may be PNG, WEBP or HEIC, which the server accepts (backend/src/domain/media.rs:66-74). Should the extension follow the content type, and should API.md list `inspection`?
15. Q-INSP-15: Should the phone check the 2000-character note limit? Android sends notes with no length check, and relies on the server's 400 (A:ui/inspection/InspectionHomeScreen.kt:266-279 vs backend/src/api/inspections.rs:667-669). The same holds for other length limits in the draft (driver name ≤ 200, location ≤ 300, fuel ≤ 16; 0026_inspections.sql:19-22). An over-long offline value only fails at sync, as a draft error. Is that acceptable, or should the phone validate?

## Invoicing & money

1. **Q-INV-1: Lifecycle vocabulary.** The brief expects draft/issued/cancelled/storno/corrective states. The code has no draft (a row is `submitting` from creation, `backend/src/repo/invoices.rs:183`) and no corrective/MODIFY invoice (`backend/migrations/0021_invoicing.sql:18` has kind `invoice|storno` only), although the chain UI labels `MODIFY` ("módosítás", `frontend/src/messages/hu.json:974`) and the sidecar supports MODIFY (`nav-sidecar/src/invoices.ts:75`). Answer needed: is a corrective invoice (Áfa tv. §170) in scope, or is "storno + new invoice" the only allowed correction?
2. **Q-INV-2: Is invoicing in scope for the web at all?** `docs/history/FRONTEND_PLAN.md:14-15` and N1 (`docs/history/FRONTEND_PLAN.md:62`) say invoicing, VAT and billing are out of scope and must not be built. `frontend/src/components/orders/InvoicesSection.tsx` and `ProformasSection.tsx` implement them. `docs/DECISIONS.md:22-23` says "Invoicing will add it". Which document is authoritative?
3. **Q-INV-3: Which date sets the FX rate?** The code uses the MNB rate on or before the **issue date** (`backend/src/service/invoicing.rs:395,1237`). Áfa tv. §80 ties conversion to the tax-point date, normally the fulfilment/**delivery date** (§55, §60), which can differ from the issue date (`delivery_date` is separately settable, `backend/src/service/invoicing.rs:73-74`). Which date is intended?
4. **Q-INV-4: Staleness window for invoice FX.** Reports refuse rates older than 10 days (`backend/migrations/0006_reporting.sql:38-41,66`). The invoice lookup `rate_on_or_before` has no lower bound (`backend/src/repo/fx.rs:79-94`), so a months-old rate would be used. Should invoices apply the same 10-day window, or a stricter one?
5. **Q-INV-5: Is the FX rate frozen at issue or re-read at submit?** The rate is not stored on the invoice. It is looked up at issue time for validation (`backend/src/service/invoicing.rs:395`) and again when the job builds the request (`:1237`). If rates are re-fetched or corrected between the two, the report may use a different rate from the one validated. Should the rate be snapshotted like the lines?
6. **Q-INV-6: VAT in HUF on EUR invoices.** Áfa tv. requires the VAT amount in HUF on a foreign-currency invoice (assumed §80/§172). The backend stores only invoice-currency VAT (`backend/migrations/0021_invoicing.sql:39-41`) and leaves the HUF figure to the sidecar/NAV via `exchangeRate`. Which component is responsible for computing and printing the HUF VAT, and with which rounding (whole forint or fillér)?
7. **Q-INV-7: HUF fillér on invoices.** The brief says HUF invoices carry no fillér. The code stores HUF with exponent 2 (`backend/src/domain/money.rs:28-33`), sends `"1397.00"`-style HUF amounts (`backend/src/domain/invoice.rs:162-169,285-287`), and the UI deliberately shows nonzero fillér (`docs/history/FRONTEND_PLAN.md:182-183`, `docs/history/REMEDIATION.md:16`). Should invoice line amounts, VAT and totals be rounded to whole forints (and in which direction), or are fillér amounts acceptable on NAV reports?
8. **Q-INV-8: Per-line vs per-rate VAT.** The backend computes VAT per line and sums it (`backend/src/domain/invoice.rs:171-186`, `backend/src/service/invoicing.rs:264-271`). NAV's `summaryByVatRate` is built inside the sidecar/open-nav (`nav-sidecar/src/schemas.ts:8-10`), which may compute VAT on the per-rate net total. The sidecar's returned `totals` are never compared with the stored totals (`backend/src/service/invoicing.rs:767-811` ignores `response.totals`). Which figure is authoritative, and should a mismatch be detected?
9. **Q-INV-9: Do non-NAV failures burn a number?** Every non-retryable sidecar error marks the invoice `rejected` (`backend/src/service/invoicing.rs:714-725`), including local `validation`/`bad_request`/`nav_error` (bad credentials), where "the document never left the building" (`nav-sidecar/README.md:405-407`). The repo says a rejected number is spent (`backend/src/repo/invoices.rs:325-326`). Is a gap in the invoice series acceptable when NAV never saw the number (accountant question, cf. `docs/DECISIONS.md:150` and Áfa tv. §169 b)), and should a `bad_request` or config error be retryable instead?
10. **Q-INV-10: Dead-lettered submissions.** After 5 failed attempts (`backend/migrations/0001_foundation.sql:92-96`) the job is dead-lettered, but the row stays `submitting` forever. That blocks new invoices for the order (`backend/src/service/invoicing.rs:358-366`), and the web keeps polling every 3 s (`frontend/src/components/orders/InvoicesSection.tsx:81-82`). What should the user see, and who resolves it (admin job retry?)?
11. **Q-INV-11: Storno of an invoice with a pending annulment, or annulment of a storno.** Annulment is allowed on `issued|stornoed` of either kind (`backend/src/service/invoicing.rs:600-603`). Stornoing is allowed while an annulment job is queued. Is an annulled storno supposed to make the original `issued` (live) again? No code does this (`backend/src/repo/invoices.rs:369-395`).
12. **Q-INV-12: Status after NAV's annulment approval.** `annulled` is set as soon as NAV accepts the annulment request, but a person may still reject it in the portal (`nav-sidecar/README.md:247-249`). Is `annulled` meant as "requested" or "approved", and is anything supposed to track the later portal decision?
13. **Q-INV-13: Customer data at submit vs issue time.** Lines are snapshotted at issue (`backend/src/service/invoicing.rs:1215-1218`). The customer (name, address, tax number) is read from the partner when the job runs (`:1229-1231,1249`), so an edit made while the invoice is `submitting` changes what is reported. Should the customer also be snapshotted?
14. **Q-INV-14: Payment method.** The API accepts any string (`backend/src/service/invoicing.rs:77-78`), and the sidecar's strict enum turns an invalid value into a `bad_request`, which then marks the invoice `rejected` (see Q-INV-9). The method is not stored on the invoice row. Should the API validate it and persist it?
15. **Q-INV-15: More than 100 order items.** The sidecar caps a document at 100 lines (`nav-sidecar/src/schemas.ts:128`). The backend does not check this before drawing a number (`backend/src/service/invoicing.rs:381-397`). Is the limit meant to be enforced upfront, or should lines be merged?
16. **Q-INV-16: Letter money format.** Letters render totals as `1270000.00 HUF` via the log-oriented `Money` Display (`backend/src/service/invoicing.rs:1073-1076`), while `Money`'s own doc says "Locale formatting is the UI's job" (`backend/src/domain/money.rs:152-153`). Should customer letters use Hungarian formatting (`1 270 000 Ft`)?
17. **Q-INV-17: Invoice due date vs. law and UI.** The due date defaults to issue + 8 days (`backend/src/config.rs:268`). The issue dialog lets the user set any date, including one before the issue date, with no client or server validation (`frontend/src/components/orders/InvoicesSection.tsx:381-392`, `backend/src/service/invoicing.rs:346-348`). Is `payment_date >= issue_date` a rule? Is `delivery_date <= issue_date + 15 days` (Áfa tv. §163) a rule to enforce?
18. **Q-INV-18: Android.** No Android invoice or proforma screen exists (`docs/integration-audit/01-system-map.md:26`). Is read-only invoice status on the phone expected (e.g. to show "paid/invoiced" on an order), or is invoicing intentionally web-only?

## Email & communications

1. Q-MAIL-1: Who may add to the suppression list? `backend/src/domain/role.rs:24` puts the "suppression list" under `ManageConfiguration` (Admin), but `backend/src/api/email.rs:351` lets `SendEmail` (Office) add entries; only removal needs `ManageConfiguration` (`:370`). Is Office meant to be able to add?
2. Q-MAIL-2: Who may read newsletter subscriptions? `backend/src/api/newsletter.rs:3-4` says the authenticated routes "need `SendEmail`", but `GET /newsletter/subscriptions` (`:38-43`) only requires login, so Designer and Viewer can read the subscriber list (personal data). Is this intended?
3. Q-MAIL-3: Does a redirect cover BCC? `backend/src/integrations/email.rs:242` says a redirect makes the message reach "only `redirect_to`", and `docs/email-google-workspace.md:106-108` says "Every message… is delivered to that one inbox". `apply_redirect` (`:243-266`) clears only `cc` and names only to/cc in the notice; `bcc` (newsletter) is not addressed. What should a redirected newsletter do with its BCC list?
4. Q-MAIL-4: Must the newsletter unsubscribe link carry a token? `backend/migrations/0024_newsletter.sql:248` generates a per-address `unsubscribe_token`, but the blast link (`backend/src/service/email.rs:848-851`) has no token, because a BCC blast cannot personalise (`api/newsletter.rs:133-134`). Is the email-typed unsubscribe (no proof of ownership) the accepted opt-out mechanism? Is a `List-Unsubscribe` header required for bulk mail (Gmail/Yahoo sender rules)?
5. Q-MAIL-5: What consent record does GDPR/Hungarian law need? Grt. (2008. évi XLVIII. tv.) 6. § requires prior, explicit consent for direct marketing, and GDPR Art. 7(1) requires the controller to be able to prove it. `newsletter_subscriptions` (`0024_newsletter.sql:241-250`) stores only `source` and `subscribed_at`; there is no consent text, IP address or double opt-in. Office adds (`api/newsletter.rs:65`) bypass any consent. Is a consent record or confirmation mail required? Must office adds be limited to existing customers?
6. Q-MAIL-6: May office staff resubscribe someone who opted out? `repo/newsletter.rs:247-249` and `api/newsletter.rs:109-110` say resubscribing clears `unsubscribed_at` ("coming back is saying yes again"), and the office add endpoint uses the same `subscribe` call (`api/newsletter.rs:65`). That means staff can silently resubscribe someone who opted out, which contradicts the rationale at `0024_newsletter.sql:232-233` ("or the next import would resubscribe someone who opted out"). Should office re-adds of an unsubscribed address be refused?
7. Q-MAIL-7: Should a newsletter unsubscribe also suppress the address? `0005_email.sql:121` says suppressions are "Addresses that asked not to receive automatic mail", while newsletter unsubscribe only touches `newsletter_subscriptions`. Should unsubscribing also add a suppression, or are the two opt-outs deliberately separate?
8. Q-MAIL-8: What does "deleting" a subscription mean? `DELETE /newsletter/subscriptions/{id}` hard-deletes the row (`repo/newsletter.rs:289-297`), which contradicts "Unsubscribing sets `unsubscribed_at` rather than deleting: the address must stay known" (`0024_newsletter.sql:232-233`). Is delete an erasure (GDPR Art. 17) path that should keep a hashed tombstone, or should it unsubscribe instead?
9. Q-MAIL-9: How many SMTP attempts does an email get? Email-level `MAX_SEND_ATTEMPTS=5` (`service/email.rs:46`) counts `email_messages.attempts`, which is incremented only by `mark_sending` (`repo/emails.rs:197`). The job's own attempts are also capped at 5 (`0001_foundation.sql:92`), but `deliver` returns `RunAt` on a transient failure, and `defer` decrements the job's attempts (`repo/jobs.rs:368`). Is the intended total 5 SMTP attempts per email, and should the backoff be driven by the email counter only?
10. Q-MAIL-10: Should a manual retry reset the attempt budget? `service::email::retry` (`service/email.rs:1287-1310`) requeues without resetting `attempts`, so an email that gave up after 5 transient failures fails again after one more attempt. `jobs::retry_failed` does reset attempts (`repo/jobs.rs:415-418`, "fresh attempt budget").
11. Q-MAIL-11: Should the rate limit cancel or defer? `decide_automatic` cancels (`domain/email.rs:111-113`) when the per-recipient daily limit is hit, so an invoice or pickup letter that exceeds 3 per day is dropped, not delayed. Is permanent cancellation of business-critical letters (invoices, `0022`) intended, or should they defer by 24h?
12. Q-MAIL-12: Should the kill switch cancel or hold invoice letters? When it is off, queued automatic mail is cancelled (`domain/email.rs:98-100`), invoice letters included (`service/invoicing.rs:1135`). Invoice letters queue regardless of the switch (no check there, unlike `automation.rs:196`). Should they be held until the switch is on instead?
13. Q-MAIL-13: What should replace the "automatic" footer on manual letters? The layout footer says "Ezt a levelet az Autotherm CRM küldte automatikusan" (`domain/template.rs:320`) and the header says "automata értesítés" (`:313`), yet the same layout wraps manual, quotation and newsletter mail (`:170-172`). Should manual letters carry different wording?
14. Q-MAIL-14: Is `lead_acknowledgement` meant to be wired up? It is seeded but unreferenced (E4 in findings). If it is meant to be sent, from which trigger, and with `{{user.name}}` resolved how on an automatic path (`service/email.rs:993` passes no sender name)?
15. Q-MAIL-15: How should a stored password interact with a switch to IP-allowlist auth? Blank strings are "treated as absent everywhere" (`api/configuration.rs:410`), but `smtp_password` is passed through unmerged (`:602`), so the stored password is kept even when the username is cleared. Which behaviour is intended for credential-less relays?

16. Q-MAIL-16: Should the web UI offer Cancel on failed and needs-review rows? The backend lets the author or an Admin cancel `queued`, `failed` and `needs_review` mail (`backend/src/repo/emails.rs:282`, 409 message at `backend/src/api/email.rs:153`). The web UI offers Cancel only on `queued` (`frontend/src/app/[locale]/emails/[id]/page.tsx:115-120`, whose comment says "own queued mail is cancellable"). Should a failed or needs-review mail be cancellable (acknowledged) from the UI?
17. Q-MAIL-17: Where should the quotation recipient come from, on web and on the server? The web dialog shows and previews only `lead.contact_email`, and shows "noEmailForQuotation" when it is missing (`frontend/src/components/email/QuotationDialog.tsx:53, 63, 85`). The backend falls back to the partner's email (`backend/src/service/email.rs:648-659`). Should the UI show the partner fallback, or should the server refuse without a contact email?
18. Q-MAIL-18: Which address should Android pre-fill for an order? Android fills the partner's email (`android/.../ui/emails/EmailComposeScreen.kt:61-64`), while every automatic customer letter uses the order contact's email first (`backend/src/service/automation.rs:169-185`, "so the two never disagree about who 'the customer' is"). Should Android use the contact email first as well?
19. Q-MAIL-19: Must the newsletter preview match what is sent? The web preview goes through `POST /emails/preview`, addressed to a hard-coded `iroda@autotherm.hu` (`frontend/src/components/email/ComposeForm.tsx:201-209`). That preview has no unsubscribe footer and resolves `{{variables}}` (as MISSING) instead of refusing them, while the real blast adds the footer and refuses any variable (`backend/src/service/email.rs:814-869`). Also, should the placeholder address come from configuration (`EMAIL_FROM_AUTOMATIC`)?
20. Q-MAIL-20: What should "needs attention" include? Admin status and the `attention` filter count only `failed` + `needs_review` rows (`backend/src/repo/emails.rs:292-298`). Automatic mail cancelled by the rails (suppressed, rate limit, kill switch) becomes `cancelled` (`backend/src/service/email.rs:1107-1111`) and is not surfaced anywhere. Should the office be told when an invoice or pickup letter was silently cancelled?

## Reports, dashboard, search & time

1. **Q-REP-1 — Workload default period.** docs/API.md:166 says all reports accept `from`/`to` with a default of the last 12 months. But `/reports/workload` defaults to 7 days (backend/src/api/reports.rs:275-278), and `/reports/stalled` takes no period at all (reports.rs:189-198). Which is correct: the code or the doc?
2. **Q-REP-2 — Does "completed" in workload include cancelled orders?** `WorkloadDay.completed` counts any terminal stage, cancelled included (backend/src/repo/reports.rs:281-283; api/reports.rs:286). Throughput leaves exit stages out (repo/reports.rs:173), and the UI labels are "Elkészült" / "completed" (ReportsScreen.kt:143; WorkloadChartsView.tsx:57). Should cancelled orders count as completed, and should they drop out of `in_workshop` on the day they were cancelled?
3. **Q-REP-3 — Where the "stalled" tile leads.** The dashboard tile links to /reports (DashboardView.tsx:133-136). The web reports page only shows workload charts (app/[locale]/reports/page.tsx:6-13). REP-71 requires the number to match the list it opens. Which list should that be?
4. **Q-REP-4 — Label on overdue blockers.** On the dashboard, overdue blockers get the badge text `t('quoteExpired')` (DashboardView.tsx:237), but the flag is blocker `is_overdue` (repo/blockers.rs:51). Is a separate "overdue" label intended?
5. **Q-REP-5 — Accents in search.** Nothing in the code or docs says whether "rakoczi" should find "Rákóczi" or "muller" should find "Müller". Search is plain ILIKE with no unaccent (repo/search.rs:64; repo/mod.rs:34-44), and the only test uses the exact form "müller" (repo/mod.rs:78). Should matching ignore accents? Also, which DB locale/ctype should be relied on for upper/lower case of ő and ű?
6. **Q-REP-6 — What a load re-run overwrites.** docs/DECISIONS.md:125-126 and docs/migration/README.md:109-110 say re-running load overwrites migrated fields. backend/src/migration/load.rs:706 says partners are coalesced so that "a re-run must not blank a column staff have since filled in", while orders get `= EXCLUDED` (load.rs:957). What is the intended rule for each entity?
7. **Q-REP-7 — Numbers on imported orders.** docs/DECISIONS.md:31 says imported orders keep whatever number they had. DECISIONS.md:127 says they are numbered `MC-{MiniCRM id}`. load.rs:90-92 and tests/migration.rs:216-217 use `order_number_field` when it is mapped. Which is the default, and must the mapped numbers be unique alongside `YYYY-NNNN`?
8. **Q-REP-8 — Error code for retrying a job that isn't failed.** docs/API.md:21 lists 409 `not_retryable`, but admin.rs:161-164 returns 409 `not_failed`. Which code should clients handle?
9. **Q-REP-9 — Tasks after migration.** load.rs:1092-1093 says "AutoCRM has no task feature and is not gaining one". Yet migration `0017_tasks.sql` exists and the dashboard has a "my tasks" section (DashboardView.tsx:76-80,317-354). Should imported MiniCRM to-dos stay as notes, or become tasks?
10. **Q-REP-10 — Valuation-date fallback on import.** If `CreatedAt` cannot be parsed, the imported order gets today's date as its valuation date (load.rs:925-931). DECISIONS.md:25-28 says the valuation date is "never today at report time". Is this fallback acceptable, given it puts historical orders into the current month's volume?
