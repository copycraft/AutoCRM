# MiniCRM migration

The highest-risk workstream: "something from the old system is missing" kills the project.
Everything here is resumable and re-runnable, and nothing is transformed until it is safely
on disk.

## Prerequisites

- MiniCRM admin rights, with the **"MiniCRM Rest API + XML szinkronizáció"** add-on active.
- `MINICRM_SYSTEM_ID` and `MINICRM_API_KEY` in `backend/.env` (never commit them).
- The normal AutoCRM `.env` (database + object storage) for `fetch`, `load` and `reconcile`.
- Run from `backend/`; data goes to `backend/migration-data/` (git-ignored).

## Week 1 spike — do this before planning around the 2 TB transfer

The whole image plan assumes the API exposes downloadable file URLs. Verify that on a handful
of projects first:

```bash
cargo run --bin autocrm-migrate -- extract --requests-per-minute 30
```

Stop it after a few dozen projects (Ctrl+C; it resumes later), then:

```bash
cargo run --bin autocrm-migrate -- manifest
```

If `manifest-summary.json` shows zero or suspiciously few files, the files are not in the
API responses — talk to MiniCRM support before going further.

## Procedure

1. **Extract** (M1). Writes raw JSON, unmodified, to `migration-data/raw/`. Safe to interrupt
   and re-run; existing files are skipped.

   ```bash
   cargo run --release --bin autocrm-migrate -- extract
   ```

   Check `raw/extract-summary.json`: category count and project count must match the MiniCRM UI.
   `missing` lists endpoints the account didn't serve.

   Per-project to-do lists are included by default (`--no-todos` to skip them). They are the
   account's project history — who said what and when — and they load into `order_notes`,
   shown on the order's Napló tab. For a company that has run its project management in
   MiniCRM for years, this is the largest single body of institutional record in the account.

2. **Manifest** (M2a). Lists every file reference with the field it came from.

   ```bash
   cargo run --release --bin autocrm-migrate -- manifest
   ```

   Compare `by_field` counts with what MiniCRM shows for a few projects. The field names in
   `by_field` are the keys you use for `image_fields` in the mapping.

3. **Fetch** (M2b). Days of transfer (2 TB at 20 Mbit/s ≈ 10 days). Start it early and let it
   run through the whole build; restart it after any interruption.

   ```bash
   cargo run --release --bin autocrm-migrate -- fetch --concurrency 4
   ```

   Progress: `fetched.jsonl` (done), `failed.jsonl` (retried on the next run). Files are stored
   once per unique sha256 under `migration/originals/`.

4. **Mapping.** Copy `docs/migration/mapping.example.json` to `migration-data/mapping.json`
   and fill it in from `raw/categories.json`, `raw/schema/*.json` and the manifest summary:
   - `categories`: each MiniCRM CategoryId → `order`, `lead` or `skip`
   - `order_statuses` / `lead_statuses`: StatusId → AutoCRM stage key
   - `image_fields`: manifest field group → `intake` / `production` / `completion` / `marketing`
   - `order_value_field`, `order_currency_field`: project fields holding value and currency, if any
   - `order_fields`: destination `orders` column → project field. Paths may be dotted
     (`Jarmu.Rendszam`). Without an entry the column stays empty for all 1000 migrated
     orders — that is how `volume_by_project_type` came to bucket every historical order
     as "(nincs megadva)".
   - `partner_fields`: destination `partners` column → contact field. Postal code, city and
     address line also fall back to `raw/addresses/{id}.json` (the AddressList endpoint).
   - `project_types` and `assignees`: every MiniCRM value → an existing `project_types.key`
     and an existing user's e-mail. **A source value with no entry stops the load**, listing
     every unmapped value at once. Nothing is written until they are all covered.
   - `countries`: MiniCRM country name → ISO alpha-2. Two-letter values pass through.
   - `order_number_field`: see "Order numbering" below.
   - `vehicle_plate_from_title`: see "Where the plate lives" below.

   Everything not mapped still lands in each row's `raw_import` column, which the
   "MiniCRM eredeti adatok" panel on every migrated partner, lead and order now shows.

   Check the mapping before writing anything:

   ```bash
   cargo run --release --bin autocrm-migrate -- load --mapping migration-data/mapping.json --dry-run
   ```

   This resolves every field with the same code the load uses, writes nothing, and prints
   per-column coverage. **A column at 0% means the mapping has no source for it.** The full
   breakdown lands in `load-dry-run.json`.

5. **Load** (M3). Idempotent upserts by `minicrm_id`; re-run as the mapping improves.

   ```bash
   cargo run --release --bin autocrm-migrate -- load --mapping migration-data/mapping.json
   ```

   Read `load-report.json` → `problems`. Photo previews are generated by the normal
   background worker, so keep `autocrm serve` running (or run it afterwards) — until it
   drains, migrated galleries show originals rather than thumbnails.
   **Stop re-running `load` once staff edit migrated records** — a re-run overwrites
   migrated fields.

6. **Exchange rates.** Backfill MNB rates for the history so EUR orders normalise:

   ```bash
   cargo run --release -- fx-backfill --from 2010-01-01 --to 2026-09-11
   ```

7. **Reconcile** (M4).

   ```bash
   cargo run --release --bin autocrm-migrate -- reconcile --mapping migration-data/mapping.json
   ```

   `reconciliation.md` compares record counts, lists missing orders, file coverage, per-order
   file mismatches, value by year, **per-column field coverage**, and a **field-level sample**:
   50 random orders and 50 random partners with every loaded column compared against the
   source JSON. Counts alone once reported ✅ on a migration that dropped every vehicle.
   **A person from Autotherm signs it off** after spot-checking orders against MiniCRM.

## What does not come across

### Stage history

**Historical stage durations are not available, and no amount of mapping changes that.**
The MiniCRM R3 API exposes a project's *current* `StatusId` and `StatusUpdatedAt` — the
date it last changed — and no per-status change log. `Api/R3/Project/{id}` carries one
status; there is no history endpoint. Every migrated order therefore enters AutoCRM with a
single `order_stages` row: its final stage, dated when that stage was entered.

Consequences, which the reconciliation report also states in writing:

- `/reports/stage-durations` and `/reports/throughput` are meaningful only for orders
  created in AutoCRM. Do not read them as covering 1992–2026.
- The traveller on a migrated order shows one visited stage. That is the truth, not a bug.
- The to-do history (`order_notes`, below) is the closest thing to a timeline for a
  migrated order, and it is usually better than a stage log would have been.

If MiniCRM support confirms a status-history endpoint for this account, it can be added to
`extract.rs` and loaded into `order_stages`; nothing else has to change.

### E-mail correspondence

Not extracted. `email_messages` starts empty, so the correspondence tab shows nothing for
any historical job.

## Open questions for Autotherm (TODO(client))

These three change what the mapping must say. The code takes either answer; nobody should
guess on Autotherm's behalf.

1. **Order numbering.** Does Autotherm print the MiniCRM project id, or its own number kept
   in a custom field? With `order_number_field` unset, migrated orders are numbered
   `MC-{MiniCRM id}`; set it to the field on the paperwork and they keep their real
   numbers. Getting this wrong means every historical order is unfindable by the number
   printed on the document a customer is holding. The load hard-fails if the chosen field
   produces duplicate numbers.

2. **Where the plate lives.** A structured field, or only inside project names? Set
   `order_fields.vehicle_plate` for the first, `vehicle_plate_from_title` (a regex applied
   to the project name) for the second. `--dry-run` reports how many orders would get a
   plate either way — run it with each candidate before deciding. A plate that never loads
   means a warranty job in 2029 cannot find its 2019 original.

3. **Which stage requires a value** (see `stage_definitions.requires_value`). Seeded on
   `production`; changeable per stage without a code change.
